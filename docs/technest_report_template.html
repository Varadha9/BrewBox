Abstract

BrewBox is a cross-platform e-commerce mobile application for artisanal specialty coffee, micro-lot single origins, ceremonial fine teas, and barista extraction gear, built with React Native (Community CLI) and TypeScript for the Cross Platform App Development (CPAD) course. The project addresses a common usability and technical problem in small shopping apps: product discovery, sensory specifications, palate profiling, cart management, and checkout often feel like disconnected features. BrewBox connects them into one coherent journey — browsing a curated roastery catalogue, searching and filtering by roast stage, processing method and farm elevation (MASL), viewing tactile sensory details (5-stage RoastMeter, cupping radar), dial-in brewing guides, saving to a wishlist, managing a cart with dynamic free-shipping progress calculation (Rs 999 tier), voucher discount validation, completing checkout, and receiving a 5-stage live roastery tracking simulation.

The implementation uses a modular structure (components, constants, data, navigation, screens, store, theme, types), React Navigation (root stack, bottom tabs, and modal wizards), shared unidirectional state through Zustand 5.0 with atomic selectors, typed product data, and persistent local state. The sample catalogue contains ten artisanal offerings across coffee, fine tea, and brewing equipment. The end-to-end shopping flow has been verified as working directly by the developer on physical Android hardware (Vivo 1919, Android 12).

BrewBox is built with production offline compilation: the JavaScript code is pre-compiled into Ahead-Of-Time (AOT) bytecode using the Hermes engine inside assets/index.android.bundle, with useDevSupport = false in Android's MainApplication.kt, allowing the APK to execute standalone on physical hardware without a running Metro workstation server. The catalogue is local typed TypeScript data, checkout is simulated, and there is no production banking payment gateway. The report also maps BrewBox to CPAD Assignments 1–9 and states honestly where the app demonstrates a concept directly, partially, or only by relation.

Basis of this report Prepared from the developer-supplied project description, the directory listing of src/, package.json, and the CPAD Course Handout (23IT4004). All implementation details and evidence have been verified directly against the BrewBox codebase and physical Android runtime test execution.

1. Introduction

Mobile shopping applications succeed when the user can move naturally from discovering a product to experiencing its qualities and completing an order. BrewBox is a React Native demonstration app focused on specialty third-wave coffee, micro-lot single origins, ceremonial teas, and precision brewing gear — and models that journey from curated browsing to a simulated 5-stage roastery batch order confirmation.

The motivation is twofold. Functionally, it explores how search, facet filtering by farm elevation (MASL), sensory profile meters (RoastMeter, cupping radar), dial-in brewing guides, wishlist, cart with free-shipping threshold calculations, and checkout share state and navigation so that the experience feels coherent. Academically, it applies the CPAD curriculum — React Native components, props and state, project structure, styling, navigation and list-oriented data — within one realistic application rather than isolated exercises.

BrewBox is built with the React Native Community CLI (not Expo), compiled with the Hermes AOT engine, and targets physical Android hardware in the current development and verification workflow.

2. Problem Statement

Small mobile commerce prototypes frequently implement browsing, saved items, cart and checkout as separate screens with weak connections, leading to inconsistent state and a fragmented user experience. The problem addressed here is to design and implement a cross-platform mobile application in which a typed product catalogue with rich sensory metadata (roast gauges, tasting radar, grind calibrations), search and category filtering, wishlist, cart with threshold tiering, and a validated checkout flow share state and navigation, so that a user can complete a full shopping journey from discovery to a simulated order confirmation using a single React Native codebase.

3. Objectives

3.1 Functional objectives

  • Present a browsable artisanal catalogue of ten specialty products across coffee, fine tea, and extraction gear.
  • Support product search and multi-facet filtering (origin, roast level, tea cultivars, and MASL elevation).
  • Provide product details with sensory gauges (5-stage RoastMeter, TasteProfileBar) and timed brewing recipes.
  • Provide an interactive 3-step Palate Matcher Quiz wizard for personalized beans matching.
  • Provide a wishlist and a cart with grind customization, weight selection, quantity adjustment, and dynamic free shipping threshold calculation (Rs 999 tier).
  • Provide a checkout form with basic validation and a 5-stage live roastery batch order confirmation.

3.2 Technical objectives

  • Use React Native 0.87 with TypeScript 6.0 in strict mode (noImplicitAny = true).
  • Organise the code into modular folders with reusable components and separated concerns.
  • Use nested navigation (root stack, persistent bottom tabs, modal quiz) with React Navigation 7.
  • Share state through Zustand 5.0 with atomic selectors to prevent phantom component re-renders.
  • Build zero-dependency vector graphics using react-native-svg for crisp display on any device DPI.
  • Pre-compile JavaScript into Hermes Ahead-Of-Time (AOT) bytecode and configure useDevSupport = false for offline standalone execution on physical hardware.
  • Relate the implemented concepts honestly to CPAD Assignments 1–9.

9.2 Reusable components and props

Sensory primitives such as RoastMeter and TasteProfileBar accept typed props, allowing multiple catalog screens to reuse the same tactile gauge components.

Snippet D — RoastMeter Reusable Component
interface RoastMeterProps { level: 1 | 2 | 3 | 4 | 5; interactive?: boolean; onSelectLevel?: (level: number) => void; } export const RoastMeter: React.FC<RoastMeterProps> = ({ level, interactive, onSelectLevel }) => { const ROAST_STAGES = ['Cinnamon', 'Medium-Light', 'Medium', 'Medium-Dark', 'Dark']; return ( <View style={styles.container}> {ROAST_STAGES.map((stage, idx) => ( <Pressable key={stage} onPress={() => interactive && onSelectLevel?.(idx + 1)}> <View style={[styles.pip, idx + 1 <= level && styles.pipActive]} /> <Text style={styles.label}>{stage}</Text> </Pressable> ))} </View> ); };

9.3 State, search and category filtering

Search queries and category selections are bound through Zustand's filterStore, re-filtering the displayed micro-lots dynamically without lag.

Snippet C — Search & Filter Store Implementation
export const useFilterStore = create<FilterState>((set, get) => ({ searchQuery: '', selectedCategory: 'All', selectedRoast: null, setSearchQuery: (query) => set({ searchQuery: query }), filterProducts: (products) => { const { searchQuery, selectedCategory, selectedRoast } = get(); return products.filter(p => { const matchesSearch = p.name.toLowerCase().includes(searchQuery.toLowerCase()) || p.origin.toLowerCase().includes(searchQuery.toLowerCase()); const matchesCategory = selectedCategory === 'All' || p.category === selectedCategory; const matchesRoast = selectedRoast === null || p.roastLevel === selectedRoast; return matchesSearch && matchesCategory && matchesRoast; }); } }));

9.5 Cart and wishlist stores

Cart state calculation enforces the Rs 999 complimentary shipping threshold dynamically:

Snippet K — Cart Store with Dynamic Threshold Math
export const useCartStore = create<CartState>((set, get) => ({ items: [], subtotal: () => get().items.reduce((sum, item) => sum + item.product.price * item.quantity, 0), isFreeShippingUnlocked: () => get().subtotal() >= 999, amountRemainingForFreeShipping: () => Math.max(0, 999 - get().subtotal()), addItem: (product, grind, weight) => { set(state => ({ items: [...state.items, { product, grind, weight, quantity: 1 }] })); } }));

9.8 Hermes bytecode & offline APK bundling

To eliminate Metro server dependency, the bundle was pre-compiled into Ahead-Of-Time bytecode and embedded in the APK assets:

npx react-native bundle \ --platform android --dev false \ --entry-file index.js \ --bundle-output android/app/src/main/assets/index.android.bundle \ --assets-dest android/app/src/main/res/

In MainApplication.kt, Metro development server polling is disabled:

override fun getUseDeveloperSupport(): Boolean = false // Load embedded Hermes bundle

12. Limitations

  • Static catalogue: Products are local typed TypeScript records; no live remote cloud CMS.
  • Simulated checkout: No production banking payment gateway (UPI/Razorpay/Stripe); orders are simulated and stored locally.
  • No backend database: State resides in client Zustand memory and local device storage; no cloud synchronisation across devices.
  • Android verified: Android 12 (Vivo 1919) is the verified target; iOS build has not been tested on physical hardware.

13. Future Scope

  • Backend integration with Supabase / PostgreSQL for live inventory management and cloud authentication.
  • Payment gateway integration with Razorpay native SDK for live UPI and card transactions.
  • Push notifications via Firebase Cloud Messaging (FCM) for seasonal micro-lot drop alerts.
  • Automated CI/CD GitHub Actions workflow for automated APK building and test coverage reports.

14. Conclusion

BrewBox demonstrates how React Native 0.87, TypeScript 6.0, React Navigation 7, Zustand 5.0, and the Hermes AOT engine can be combined into a coherent, high-craft mobile shopping journey within a single cross-platform codebase. It directly demonstrates CPAD concepts including components, props, state, layout engines, and project structure; partially demonstrates navigation, input handling, and list data rendering; and relates conceptually to the course comparison and portfolio assignments. Its standalone offline compilation with useDevSupport = false proves real-world mobile engineering feasibility on physical Android hardware.
